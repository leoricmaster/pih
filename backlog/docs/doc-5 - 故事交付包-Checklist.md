# 故事交付包 Checklist（标杆蒸馏）

来源：TASK-1.01.01（m-0 首故事）按标杆标准交付后蒸馏。后续故事照此执行；
项目级流程事实源与之一致，冲突时以本表+README「测试分层与 CI」为准并回来修订。

## 1. 交付包定义

一个故事的「完成」= 代码 + 测试 + 流程纪律 + 文档同步 + 证据，五者齐备才 finalization：

1. **前置复核**：实测存量与计划假设对齐（读代码不臆测），偏差先回来对齐再动手
2. **设计文档**：`docs/design/TASK-ID-design.md`，经用户评审后进入实现
3. **TDD 切片**：每 AC 一至多个切片；每切片 红→绿→重构→（ruff+相关层测试绿）→细粒度 commit→task notes 记证据与偏差
4. **测试分层落位**：新用例显式选层（unit/contract/integration/live）并在设计文档记理由；能降层就降层（CI 可运行集单调增长）
5. **文档同步**：README 相关章节、事实源偏差闭环（架构级→ADR+用户确认；小偏差→设计文档 §偏差 与 notes）
6. **finalization**：逐 AC 客观验证（测试名/命令+输出）才勾选；DoD 逐条核对；final-summary 命名验证证据；置 Done

## 2. 设计文档模板（`docs/design/TASK-ID-design.md`）

- **存量映射**：AC ↔ 既有代码 ↔ 增量表——增量最小化是默认姿态
- **决策记录**：D1..Dn，每条=决策+理由+被否选项；不写代码级细节（防成为代码另一表述）
- **接口与状态语义**：新路由/函数签名、状态机与三态类语义（如有）
- **测试分层**：每类用例的层位与理由
- **事实源偏差与裁决**：实现中发现的 doc/原型/schema 偏差，逐条闭环
- **AC 证据清单**：AC → 计划取证的测试/命令（占位，finalization 前补实测）

粒度红线：人类可评审（每节 ≤ 300 字级），不复述实现。

## 3. 证据格式

- **测试类**：`文件::类::用例` + 层位 + 一句话说明锁什么语义；先红后绿须记录「红的原因」
- **命令类**：命令 + 输出摘录（状态码/关键行）；冒烟（curl/uvicorn）记 URL+状态码+关键文案
- **页面类**：优先 DOM/文案断言的自动化用例；必要时截图（存 notes 引用）
- 反例：以「代码存在」「应能通过」充当证据——一律不算

## 4. 测试与 CI 策略

- 分层表与运行方式、CI 固定内容（ci.yml 跑什么）：以 README「测试分层与 CI」+ ci.yml 注释为事实源，本文不重述
- 新用例默认目标=进 CI（unit/contract），进不了时在设计文档记理由
- 用例降层单向：live→integration→contract→unit 允许，反向须说明
- 依赖容器的用例在模块 docstring 写启动前置（如「需 docker compose up postgres minio」）
- 单测禁止真网络/真时钟；编排缝（如 `run_probe`）在模块命名空间引用依赖供 monkeypatch
- **integration 层必做**：跨接线缝的 AC 各至少一条端到端用例（DB 往返 / 真实适配器注册表 / route→service→repo / compose 网络——单测 monkeypatch 会掩盖此类接线 bug；TASK-1.01.01 实证：web 进程适配器注册表为空仅 integration 抓到）。纯算法 AC 不强求

## 5. 验收材料包（人类验收评审前例行提供）

来源：TASK-1.01.01 首轮验收反馈固化。五问固定结构，全部客观证据，禁止自评式断言
（「应该可以」「质量良好」不算）；允许如实回答「无新增发现/无更新」，但不允许省略问题项：

1. **中长期文档更新**：架构/README/术语表等维护性文档有无更新；有则逐项概要，无则说明为何不需要
2. **自动化测试报告**：全量结果（命令+通过数）+ 本故事新增用例清单（`文件::类::用例`+层位）
3. **产品增量与验收路径**：增量以旅程锚定——本轮新增/改变了哪条旅程的哪一步（doc-6）；可打开的页面/入口；逐步验收操作（URL+操作+预期文案）
4. **腐烂坏味道**：文档/代码/框架（含测试框架）漂移与腐化的客观观察，附位置引用；实现方最清楚，宁多报不漏报
5. **下一步建议**：按技术演进/技术债/产品演进三轴给建议；需排期的提 backlog 需求单，并给理由

页面类故事附加：**与旅程及原型 IA 对照**——先对 doc-6 旅程步骤（增量落在哪一步、
旅程前后衔接是否走通），再对原型布局级对照（导航/分区/层级，不只字段级）；
偏离须先给理由与修改意见、讨论通过后再改（旅程为上位参照，原型首先被参考）。

落地机制：本节为内容契约（「提供什么」）；CLAUDE.md 触发线（「何时提供」）；
2 个故事后再评估是否蒸馏为 skill（收集命令的自动化，不提前固化）。

## 6. 验收中发现问题的处置（直接修 vs bug 单）

**验收面口径**（用户裁定 2026-09-03）：每张单必须端到端**可客观验收**——
用户故事（story/bug）从**用户视角**验收（页面/CLI 可操作、原型对照、AC 逐条复现）；
债务/基建单（chore）从**工程视角**验收（度量前后对比+回归全绿+行为零变化承诺）；
不开无验收的口子。

判据两问：**还在当前故事的验收循环内吗**（故事未 Done、问题在本故事 AC 范围内）；
**需要排期/方案讨论吗**（跨故事、修法有分歧、当下修不了）。

- 验收循环内 + 本故事范围 → **直接修** + task notes 留痕（问题/原因/修法/防再发）——
  故事未 Done，修复是「把故事做完」的一部分；开单反而把本故事欠账挪到别处
- 已 Done 后发现 / 跨故事范围 / 修法有分歧 / 需外部依赖或大重构 → **backlog bug 单**
- bug 单的独立价值=质量信号统计：Done 后开的单即**验收逃逸缺陷**，
  可量化「验收材料包是否在起作用」；验收内直接修不计逃逸、只记 notes
- 实证：TASK-1.01.01 首轮验收三处（结论行告警聚合/侧边栏 IA/CI 注释引用漂移）
  均属验收循环内——零 bug 单、notes 全留痕

## 7. 遗留改进（不阻塞后续故事）

遗留改进直接立 backlog 单，不在本文档留痕（已完成内容不入文，免文档失控；历史项已落 TASK-5）。
