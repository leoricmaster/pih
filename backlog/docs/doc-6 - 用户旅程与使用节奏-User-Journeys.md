- 定位：**需求层的体验事实源**。doc-1 回答「为什么做与做什么」；本文回答「谁以什么节奏、从哪进入、走什么路径、以什么结束」；doc-2 回答「技术如何支撑」。IA（doc-2 · 原型 prototype.html）与需求树（backlog tasks）以本文为上位参照：**界面与故事须能认领旅程步骤；旅程步骤须有界面与故事归宿**。
- 来源：Web 验收轮感触（IA/原型缺用户旅程层——逐故事更新后「不知道怎么用、界面割裂」，D5/D13 类集成问题在走查中现场才暴露）；决策日志 §5 旅程版走查蒸馏。行业参照：Garrett 五层模型（战略→范围→结构，本项目曾自战略直跳结构）、Patton 用户故事地图（主干=用户活动时序、发布切片横切主干）、场景化 UAT（按「用户的一天」排练验收）。

## 1. 角色模型：使用模式 × 节奏（非 Persona，J-1）

单操作员内网部署（ADR-006），角色=**一人多帽的使用模式**（doc-2 §2），不做真人 Persona：

| 角色（模式） | 触发 | 节奏 | 入口 | 核心动作 | 结束态 |
|---|---|---|---|---|---|
| 运营者 | 每工作日开始；告警事件；发现新信源 | 每日 ~5 分钟 + 每周巡检 + 事件驱动 | `/`→铃铛→`/verify`→`/sources` | 确认自运转、消化异常、终态核实（终态人工 ADR-002）、接入新源 | 铃铛清零、无积压、健康全绿 |
| 消费者 | 真实问题冒出 | 随需（北极星计数本体） | `/` | 组合筛选→详情→溯源→引用 | 带可引用、可溯源的答案离开 |
| 录入者 | 参会/访谈/见闻回来 | 事件驱动 | 未点亮（原型 intake） | 丢素材 30 秒入库、自动结构化 | 与自动采集同链入库 |
| 求证者 | 冒出假设 / 命中提醒 | 登记随需 + 命中驱动 | 未点亮（原型 hypo） | 登记假设→收证据→下结论→反哺（ADR-010） | 假设转结论（判断层资产） |
| 消费者·Agent | 规划 Agent 调用 | 随需 | 演进：只读 JSON API | 同源检索 | draft-001 |

## 2. 现行旅程剧本（MVP 已点亮）

> 每条 = 触发 + 入口 + 步骤（每步含期望的可见反馈）+ 结束态。**恒定剧本存本文**；每轮验收的活体数据快照与现场操作建议存当轮决策日志（实例层），不回写本文。**走查铁律**：任何一步「不知道下一步去哪 / 该做什么」记旅程级问题，优先于页面级观感。

### 旅程 A｜运营者晨检（每工作日 ~5 分钟）

1. `/` 扫检索列表——extracted 成品行、事件核实状态可见；晨间应有「今日新增」（到点可见）。
2. 看铃铛——无角标即过；有角标先走旅程 C。
3. `/verify`（唯一人工工作台，ADR-011 两视图的运营面）：积压提醒应空、pending 应≈0（无人值守处理链接力）；有升级条件的事件做终态——确认→多源确认 / 证伪→条目从检索默认消失；needs_manual 有则重放；审计折叠区（filtered_out/dead）按漏报审计偶查，误杀可重放救回。
4. `/sources` 健康列全「正常」即收工。

**结束态**：铃铛无角标 + 无积压 + pending≈0 + 健康全绿；达不到即旅程级断点，逐条记录断在哪一步。

### 旅程 B｜检索消费者按需查证（随需，带真实问题来）

1. `/` 组合筛选五要素（主体/事件类型/时间范围/标签/置信度「≥ 档」）逼近问题。
2. 空态有出路：「无结果，建议放宽条件」。
3. `/intel/{id}` 分区读取——结构化字段 + Admiralty 双维注解；推断条条含「依据」；事实/推断强制分离。
4. 溯源：原始链接 + 原文快照双入口——敢引用的最后一环。
5. 事件上下文：核实状态 + 完整跃迁时间线（system 自动 / operator 人工）。
6. （可选）反馈纠错——旅程 F 的入口已在详情页。

**结束态**：带着可引用、可溯源（Admiralty 评级 + 原文）的答案离开；一次真实检索 = 北极星一次计数。

### 旅程 C｜告警处置（事件驱动）

1. 点铃铛——下拉内完成分诊（信源名 + 失败原因；现在处理 / 稍后）。
2. 需要时「查看全部历史」→ `/notifications`（未读/历史分组）。
3. 处置：`/sources` 定位异常源，按根因行动（修复 / 启用流程 / 明确放任）。
4. 闭环：「标记已读」→ 角标归零。

**结束态**：每条告警要么已处置、要么有意识放任；角标清零，回到旅程 A 节奏。

### 旅程 I｜信源接入（事件驱动 · 发现值得盯的新源）〔v1.1 复审新增〕

1. 触发：发现值得盯的新源（行业站点 / 竞品资讯页 / 调研线索）。
2. 领域包 YAML 登记信源（id/名称/类型/URL/列表页/层级/可靠性/频率，enabled: false）——缺必选字段加载被拒并指行号，不半截加载。
3. 信源页 `/sources` 点「试抓取」→ 四维报告（robots / 列表页 / 详情 / 快照）逐项标成败；robots 拒绝即止步（合规 NFR）。
4. 报告认可 → YAML 中 enabled 置 true（Git 留痕；人是最终环节，工具不改 YAML，ADR-001/002）。
5. 次日：采集节奏生效——晨检 A1 见新源条目、健康列「正常」。

**结束态**：新源进入正常监控循环（交棒 A/C 接管）；试抓报告留档为启用依据。

## 5. 使用与复审机制

1. **验收走查**：页面类故事的验收路径以旅程锚定——增量答「新增/改变了哪条旅程的哪一步」（doc-5 §5 已联动）。
2. **IA / 原型仲裁**：结构层争议（D13 类）以本文为上位参照裁定；原型仍是草案，随裁定反向更新。
3. **三项复审**（每基线版本后例行）：①**原型合理性**——✅ 2026-09-04 首轮随 J-4 执行（配置页/仪表盘移除；/feedback 半亮与 intake/hypo dark 随各自旅程点亮）；②**切分维度**——✅ 2026-09-04：§3 故事地图落稿（旅程第二索引，epic 能力组织不变）；③**切分完备性**——✅ 2026-09-04：双向判据查毕，无孤儿产品单、无两不靠缺口；旅程 I 为复审新增（1.01.x 归宿补齐）。发现明细见 §8。

## 6. 与北极星、验收门槛挂钩

- 北极星（周均检索使用）= 旅程 B 的周频次；「被使用」的操作化定义 = 各角色旅程按节奏真实发生。
- Charter §8 风险 1 的缓解「以开发者本人真实使用验收」= 按本文旅程每日/每周真实排练。
- 无人值守 4 周门槛的日常形态 = 旅程 A 每日收工态持续成立。
