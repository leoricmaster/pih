- **本文档定位**：需求的事实源与导读——开发前是具体的需求说明，开发后凭状态位反映实现现状

**编写约定**：

1. **结构**：Epic（用户目标）→ Feature（用户能力）→ Story（可验收的用户故事）；SPK 为特殊 Story，产出是知识/决策而非功能；
2. **分级明细**：按需求成熟度分层——核心闭环（故事句 + 全量 Gherkin AC）/ 已规划（故事句 + 验收要点）/ 远期占位（仅故事句），AC 的有无即分层标志。分层只决定"写多细"，不是排序依据；从待开发需求中选哪个先实现，由 Sprint 规划决定；
3. **状态**：Story 标题带状态位（待开发 / 进行中 / 已交付 / 已废弃），随交付更新；
4. **AC 与测试对接**：Gherkin AC 落 `.feature` 文件，Story ID 作标签（如 `@S1.1.1`），需求→测试双向追溯；实现层工具选型随代码库演进。

## 0. 角色模型（Persona）

> 角色按职责定义，是接口而非具体人员——每个角色均可由人或 Agent 承担（见需求文档 §3.1）。

| 角色 | 代号 | 一句话诉求 |
|---|---|---|
| 情报运营者 | **运营者** | "我要能控制情报质量与信源健康，系统别给我添乱" |
| 主动消费者 | **消费者** | "我要能查到可信的竞品情报，并直接用于规划决策——Agent 亦然" |
| 被动消费者（简报读者） | **读者** | "定期给我一份看得懂的简报" |
| 信息贡献者 | **贡献者** | "我参会/访谈得来的信息，30 秒内能丢进系统"（后续方向） |

（初期各角色由同一人承担，见需求文档 §2；Agent 承担消费者/贡献者为其自然扩展，接口已预备——S1.1.4 与录入网关。）

## EPIC-0 开发去风险（Spike）

**目标**：以最小成本验证主要技术与领域风险，产出回写需求文档与 ADR。SPK 条目不交付用户功能。

#### SPK-1（已交付）信源可抓取性验证

> 摸底候选信源反爬强度，锁定 ≤10 信源清单。检验对象：需求文档 §7"信源反爬/失效"风险。

#### SPK-2（已交付）LLM 抽取准确率摸底

> 少量样本试抽，评估抽取提示词工作量。检验对象：需求文档 §7"LLM 抽取错误"风险。
> 交付：2026-08-25，3 轮提示词迭代（v1/v2/v3），25 样本 MiniMax-M3 实测。枚举命中率 52–56%，字段准确率 25–31%（瓶颈为自由文本严格相等评分口径）。报告见 `spikes/spk2-extraction-probe/spk2-report.md`。

#### SPK-3（已交付）LangGraph + 自有模型服务连通性验证

> 端到端跑通一次抽取。决策语境：ADR-004 后果节。
> 交付：2026-08-25，LangGraph 1.2.11 三节点图（粗筛→抽取→校验）跑通 25 样本，端到端成功率 92%（23/25 产出完整 schema），API 调用成功率 100%。粗筛 kept 92%（2 条假阴性，锂矿/期货口径偏窄），validate 重问率 22%。决策结论：ADR-004 维持。报告见 `spikes/spk3-langgraph-e2e/spk3-report.md`。

#### SPK-4（待开发）第二领域纸面套模

> 以物流机器人领域套用五元模型 + 领域包 schema，记录覆盖缺口。决策语境：ADR-001 后果节。

> 行动项（非 Spike）：法务确认招投标/招聘数据边界，Sprint 0 内完成，结论回写需求文档 §6。

## EPIC-1 消费者检索与使用情报

**用户目标**：作为消费者（人或 Agent），我在做产品规划/设计/专题分析时，能快速查到可信的竞品情报，并清楚每条情报的可信度与出处。

### F1.1 结构化筛选与浏览

#### S1.1.1（已交付）多条件组合筛选

> 作为消费者，我想按 主体/事件类型/时间范围/标签/置信度/事件核实状态 组合筛选情报列表，以便快速定位某类信息。

> Sprint 5a 备注：Web 列表 + JSON API 同源交付（ADR-006）——FastAPI 单 app 双出口，QueryService 共用过滤/排序；主体/事件类型/标签/置信度（admiralty 精确）/信源/时间范围（since-until）/游标分页（before）。AC1/AC2 满足；AC3「已过期标识」待时效管理器 Sprint，expires_at 上线后自动激活（不交付子句）。事件核实状态列占位「待事件模型上线后自动激活」。排序简版 admiralty_code ASC NULLS LAST + fetched_at DESC，完整 score 待事件+时效 Sprint。

```gherkin
AC1: Given 情报库已有 ≥60 条情报
     When 消费者选定"主体=三一 + 事件类型=新品发布 + 近90天"
     Then 列表仅展示同时满足三个条件的情报
     And 每条显示 标题、主体、事件类型、置信度、所属事件核实状态、采集时间

AC2: Given 筛选结果为空
     Then 页面提示无结果，并建议放宽条件

AC3: Given 情报已超过有效期
     Then 列表中该条显示"已过期"标识且排序靠后
```

#### S1.1.2（已交付）情报详情页

> 作为消费者，我想查看单条情报的完整信息（事实描述、推断、来源快照、所属事件状态与核实流转），以便独立判断其可信度。

> Sprint 5a 备注：Web 详情 + JSON API 详情同源交付——schema 全字段 + 事实/推断分区 + 原文 URL + 快照占位入口；事件核实状态与跃迁历史区占位「待事件模型上线后自动激活」，event 表上线后查询服务自动填实。

```gherkin
AC1: Given 任意一条情报
     When 打开详情页
     Then 展示 schema 全部字段（含事实/推断分区展示）
     And 展示所属事件的核实状态与完整状态跃迁历史（自动跃迁标注 system）
     And 提供原文快照与原始链接两个入口
```

#### S1.1.4（已交付）只读查询 API（Agent 消费者）

> 作为 Agent 消费者（如产品规划 Agent），我想以 JSON API 按与 Web 相同的条件组合查询情报，以便程序化消费情报库，而非解析网页。

> Sprint 5a 备注：JSON API 同源交付（ADR-006）——与 Web 列表/详情共用 QueryService，同条件返回同 id 集合与排序（AC1 集成测试断言）；Bearer token 鉴权（PIH_API_TOKEN env，hmac.compare_digest 常量时间比较）；AC2 响应含 event_verification_status 占位字段 + event_verification_note「待事件模型上线后自动激活」；Web 内网默认开放不鉴权。

```gherkin
AC1: 同源一致性（ADR-006）
  Given 情报库已有任意数据
  When 以相同筛选条件分别请求 Web 列表与 JSON API
  Then 返回的情报集合与排序完全一致

AC2: Given 外部系统携带有效凭据调用 API
  When 提交 主体/事件类型/时间/标签/置信度 组合查询
  Then 响应含 情报ID、事实/推断分区、来源引用（URL+快照）、置信度、所属事件核实状态

AC3: Given 缺失或无效凭据的调用
  Then 拒绝访问，不返回任何情报数据
```

### F1.2 自然语言问答

#### S1.2.1（待开发）带引用的情报问答

> 作为消费者，我想用自然语言提问（如"竞品 X 的遥控功能迭代历史"），得到答案且每个结论都标注来源情报、原始链接和置信度，以便判断是否敢采用。

验收要点：
1. 每个事实性结论附引用（情报 ID + 来源名称 + 置信度标签），可点开详情与原文快照；
2. 无置信度高于 C3 的相关情报时，如实回答"暂无可靠情报支持"，不编造；
3. 精确型号 token（如 SY375）可召回（混合检索生效）。

#### S1.2.2（待开发）追问与多轮对话

> 作为消费者，我想对上一轮答案追问（"那 Y 竞品呢？"），系统能理解上下文，以便连续深挖一个主题。

验收要点：
1. 追问省略主体时，沿用上一轮的主体与语境作答。

### F1.3 竞品对比

#### S1.3.1（待开发）功能矩阵对比视图

> 作为消费者，我想勾选 2–5 个竞品，输出功能项对比表（有/无/规划中），以便做竞争分析。

验收要点：
1. 勾选 2–5 竞品 × 功能域（如"远程遥控"）输出对比表，单元格取值 有/无/规划中/未知；
2. 每个"有"的单元格可点击查看支撑情报引用。

#### S1.3.2（待开发）功能矩阵维护

> 作为运营者，我想基于已核实情报维护竞品 × 功能矩阵（有/无/规划中），以便对比视图与专题分析有据可读。

验收要点：
1. 矩阵单元格的取值须关联支撑情报（引用 + 置信度）；
2. 新情报入库或所属事件终态变化时，提示受影响单元格复核。

#### S1.3.3（待开发）竞品档案与参数矩阵（远期占位）

> 作为消费者，我想查看每个竞品的档案页（基本信息 + 情报聚合）与关键性能参数矩阵，以便快速掌握竞品全貌。

（需求文档 §4.4"两类结构化资产"；表结构先行设计，自动维护远期实现。）

### F1.4 专题调研（远期占位）

> 作为消费者，我能发起专题调研任务（如"3D 引导系统竞品对比"），智能体限时深挖并产出报告。

（需求文档 §4.8；立项时再分解为 Story。）

## EPIC-2 读者接收情报简报

**用户目标**：作为读者/消费者，我不主动检索时，也能定期收到精选情报，重要事件当日知晓。

### F2.1 定期简报

#### S2.1.1（待开发）周报自动生成与推送

> 作为读者，我想每周一收到上周情报周报（按事件类型分组 + 待核实清单 + 成本与质量指标），以便 5 分钟掌握行业动态。

验收要点：
1. 每周定时（可配置）推送，按事件类型分组、重大事件置顶、每条含置信度标签；
2. 附两项运营指标：采集成功率、待核实积压量；
3. 无新情报仍推送并说明"本周无新增"，不静默。

#### S2.1.2（待开发）月报：趋势与格局

> 作为读者，我想每月收到趋势性归纳（竞品动态对比、值得关注的弱信号），以便把握格局变化。

验收要点：
1. 含各竞品本月事件计数对比、事件类型分布变化、环比突出变化（如"某竞品专利公开数环比 +200%"）；
2. 单列"弱信号"章节——仅出现于 L4 信源且未升级的事件，附置信度；
3. 无新情报仍推送并说明"本月无新增"。

### F2.2 重大事件即时推送

#### S2.2.1（待开发）一级信源重大事件当日推送

> 作为消费者，一级信源（官方）出现新品发布/中标/高管变动时，我想当日收到推送，以便及时响应。

验收要点：
1. 满足 来源层级=L1 且 事件类型∈{新品发布,中标落地,组织人事} 的情报完成入库后，30 分钟内推送（事实摘要 + 置信度 + 详情链接）；
2. 同一事件多源重复报道不重复推送，仅在原推送下追加新来源。

## EPIC-3 运营者维护情报质量

**用户目标**：作为运营者，我能高效处理待核实情报、管理信源与领域包，控制系统质量。

### F3.1 人工核实

#### S3.1.1（待开发）待核实队列处理

> 作为运营者，我想在一个队列里逐条查看待人工处理的情报（低置信、冲突、已具备升级条件的事件），一键确认或证伪，以便控制入库质量。

```gherkin
AC1: Given 存在需人工处理的情报/事件
     When 运营者打开核实队列
     Then 按 置信度升序 + 采集时间升序 排列（低置信、最老的优先）
     And 队列包含三类：低置信度情报、相互冲突情报、已具备升级条件的事件

AC2: Given 运营者对"单源确认"事件点击"确认"（已具备升级条件）
     Then 事件状态跃迁为 多源确认（人工终核），写入 verification_log（操作人、时间、原状态、新状态）

AC3: Given 运营者点击"证伪"并填写理由
     Then 所属事件状态跃迁为 已证伪，理由写入日志
     And 该事件下情报在检索结果中默认隐藏

AC4: Given 事件已具备升级条件（双独立信源）但运营者未处理
     Then 事件保持 单源确认 状态，不自动跃迁为多源确认（终态必须人工）
```

#### S3.1.2（待开发）积压自动降级

> 作为运营者，待核实超过 7 天无人处理的情报自动降级归档，以便队列不被旧数据淹没。

```gherkin
AC1: Given 一条情报待核实状态持续 7 天
     When 定时任务执行
     Then 其检索权重降级，并在巡检报表"积压提醒"中列出
```

#### S3.1.3（待开发·下 Sprint 候选）消费页人类反馈动作

> 作为消费者/运营者，我想在情报详情页对抽取结果一键标记反馈（主体错了、事实不准、事件类型错、不该入库），以便上游 process 层 prompt/粗筛据此迭代，形成人机闭环。

> 优先级提升依据（Sprint 5a 验收）：粗筛误放与抽取误读是**批次性**问题，非个例——13 条里 5 条时政/科普类误入库或主体错抽（电池包技术文主体="未知"仍 extracted、政府调研文主体误读页面栏目名"铁建投资"）。错误样本只能靠人在消费时顺手标记积累；无此闭环则粗筛口径收紧全靠盲调，误杀真情报的风险不可控。与 S3.1.1 离线队列互补：本卡是详情页内联反馈，路径更短，消费即梳理。

```gherkin
AC1: Given 消费者打开情报详情页
     When 看到"主体"字段与原文不符
     Then 可点击"主体错了"反馈按钮，弹出输入框填正确主体（可从主体清单选或自由输入）
     And 反馈记录写入 feedback 表（item_id, field=subject, wrong_value, correct_value, user_id, ts）

AC2: Given 消费者看到事实描述不准
     When 点击"事实不准"反馈按钮
     Then 可选择具体哪条事实（按 ；拆分后的列表项）并填说明
     And 反馈记录标注到具体事实项级别

AC3: Given 消费者认为这条不该入库（粗筛漏放）
     When 点击"不该入库"反馈按钮
     Then 反馈写入 feedback 表，type=should_filter
```

## EPIC-4 系统自动生产情报（无人值守底座）

**用户目标**：作为消费者，系统 7×24 自动盯信源并产出结构化情报，我看到的永远是新数据，无需任何人手工搬运。

> 技术型 Story：故事以用户价值表述，验收偏技术指标，测试以集成/端到端为主。

### F4.1 自动采集

#### S4.1.1（待开发）按频率自动抓取与快照存档

> 作为消费者，注册的信源按其频率自动更新，且每条原文都存档快照，以便我日后能回溯原文。

> AC1 跨 Sprint 满足：Sprint 2 已交付快照存档（MinIO + RawItem.snapshot_id），Sprint 3 已交付入库门控（intel_item.content_sha1 UNIQUE = 无快照不入库的下游约束）；本卡剩余范围 = APScheduler 调度器 + AC2 去重 + AC3 重试与 inbox。

```gherkin
AC1: Given 信源配置频率为每日
     When 调度时间到达
     Then 系统自动抓取新内容，并为每条新内容生成原文快照
     And 无快照的内容不允许进入后续流水线

AC2: Given 抓取到与历史内容 URL 指纹相同或相似度 > 阈值 的内容
     Then 自动去重，不产生重复情报

AC3: Given 抓取失败（网络/反爬）
     Then 按指数退避重试 3 次，仍失败计入信源健康统计
     And 原始内容先落盘 inbox，处理失败不丢失、可重放
```

#### S4.1.2（已交付）相关性粗筛

> 作为消费者，系统只把与领域相关的内容送入后续处理，以便情报库不被噪音稀释。

> Sprint 4 交付：小模型（tier=small）二分类粗筛，LangGraph 图首节点；「粗筛日志」以行级标记实现——判无关的条目 `process_status='filtered_out'` 保留在 intel_item（不物理删除），SQL 可审计（架构 §8 不丢弃口径）；粗筛 API 失败按灰条目保留走抽取（SPK-3 结论）。AC1「关键词 +」部分未做——LLM 二分类前置无关键词层，漏报审计靠行级标记 + LLM env 关闭时可全量重跑。

```gherkin
AC1: Given 一条新抓取内容
     When 关键词 + 小模型二分类判定为不相关
     Then 该内容被丢弃并记录到粗筛日志（供漏报审计）
```

### F4.2 自动核实与结构化

#### S4.2.1（已交付）自动结构化抽取

> 作为消费者，每条入库情报都按 schema 填好主体、事件类型、量化参数、标签，以便我能结构化筛选而非读原文。

> Sprint 4 交付：LangGraph 三节点图（粗筛→抽取→校验）+ `pih process` 批处理 CLI；领域包 v0.2.0 单一事实源（event_types 枚举 + 标签树 + 提示词占位符加载期校验）；intel_item 增 11 结构化列（迁移 0002，tags JSONB + GIN）；校验重问 ≤3 轮，API 重试独立计数（SPK-3 遗留契约）。
>
> 口径备注：AC1「标签均非空」按字段存在 + 合法性满足——标签可为空数组（`[]`），行业统计/组织人事类情报常无技术标签，强制非空会制造假标签；主体/事件类型/事实描述仍严格非空。AC2 满足：重问耗尽 → `process_status='needs_manual'`，条目保留可查（集成测试 AC2 验证）。
>
> 已知质量问题（Sprint 5a 验收发现，待 S3.1.3 反馈闭环积累样本后迭代）：① 主体抽取会把页面装饰元素（栏目名/作者名）当主体——如 cehome 「海南省省长刘小明调研临高金牌港项目」主体被抽成"中国铁建投资集团"（实为页面栏目"铁建投资"被误读，且违规加"中国"前缀）；② 粗筛对"政府调研项目"类新闻漏放（同批次「国铁集团党组学习」被正确过滤，但本条漏网）——粗筛阈值或 prompt 对"非竞品但含工程机械关键词"的场景判定不稳。修法分工：增量由 S4.2.3 后验门拦截（主体"未知"→needs_manual），根治靠 S3.1.3 反馈数据 → prompt 加"主体必须是正文出现的主语实体，不得取栏目名/作者"规则 + 粗筛加负样本 few-shot。

```gherkin
AC1: Given 一条通过粗筛的内容
     When 结构化抽取完成
     Then 情报记录的 主体/事件类型/事实描述/标签 均非空
     And 事实与推断分字段存放，推断字段必须含依据

AC2: Given LLM 返回的结构化输出未通过 schema 校验
     Then 自动重问（≤3 次），仍失败则条目降级为"待人工"，不丢弃
```

#### S4.2.2（待开发）自动预评级与交叉印证

> Sprint 4 备注：AC1 已以简版满足——来源层级继承 source 表 reliability（collect 期 sync），Admiralty = reliability × 信息可信度（抽取 prompt 输出 1–6 枚举），extracted 条目 `admiralty_code` 非空（如 B2）；「核实引擎处理完成」中的核实流程未做。AC2/AC3（事件聚类/双独立信源跃迁/事件表）待事件聚类 Sprint（先例：S4.1.1 AC1 跨 Sprint 备注）。
