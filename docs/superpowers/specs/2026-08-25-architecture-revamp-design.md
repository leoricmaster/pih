# 架构文档评审与修订设计（ADR 拆分 + 分层重构）

- 日期：2026-08-25
- 输入：《Architecture.md》V0.6（含 13 个内嵌 ADR）、《Product Requirements.md》V0.7、《情报中心-Backlog.md》V0.6
- 产物：新版 `docs/Architecture.md` + `docs/adr/` 7 个独立 ADR 文档

---

## 1. 目标

1. ADR 从架构文档拆分为独立文档，数量 13 → 7，每个 ADR 只保留"真决策"（有真实 alternatives、影响全局、后人需要知道 why）；
2. 每个 ADR 统一结构：**问题 → 可选方案 → 各方案优缺点 → 决策 → 理由**，风格简洁精炼；
3. 架构文档按"由外到内、由静到动"分层重构，逻辑紧密、便于阅读；
4. 全部示意图改用 mermaid（替换 ASCII 图）；
5. 不留历史映射——项目处于开始阶段，新 7 个 ADR 直接作为最初版定稿（编号 001–007）。

## 2. ADR 方案（已选定方案 A）

- 优点：…
- 缺点：…

### 方案 B：<名称>

## 5. 明确不做

- 不建立 ADR 状态流转机制（提案/接受/废弃流程）——项目 1 人开发，"状态：已接受"固定即可；
- 不保留原 13 个 ADR 的历史映射表——新 7 个即最初版；
- 不为 mermaid 图引入渲染工具链——GitHub 原生渲染即可。

## 6. 验收标准

1. `docs/adr/` 存在 7 个 ADR 文件，每个符合统一模板（问题/可选方案/优缺点/决策/理由/后果）；
2. 新版 `docs/Architecture.md` 按 10 节大纲组织，包含 ≥5 个 mermaid 图（上下文/容器/逻辑分层/数据流/状态机/ER 至少各一），无 ASCII 图；
3. 三份文档 + ADR 文件中的每处 ADR 引用都指向新编号的正确语义（逐一人工核对：旧 002→新 002、旧 004→新 003、旧 006→新 004、旧 009+011→新 005、旧 007+013→新 006、旧 012→新 007；旧 003/005/008/010 的引用改指正文对应节），无残留旧语义引用；
4. 原 13 个 ADR 的语义无丢失：每条内容要么在新 ADR 中，要么在正文对应节中；
5. git 提交包含：Architecture.md 重写、adr/ 新增、两份文档的引用同步。
