## 0. 背景与目标

用户对 Backlog 的定位：**把需求梳理清楚**；从全量未实现需求中选择哪个先实现，交给后续 Sprint 实践。Backlog 渐进明细，逻辑清晰、便于管理与演进，不堆砌。管理工具未定，希望支持树形结构与渐进明细。

Backlog 的双重生命周期：完成需求前，作为具体的需求文档；完成开发后，让后续人员快速知晓产品实现现状。

### 文档头编写约定（四条）

1. 结构：Epic（用户目标）→ Feature（用户能力）→ Story（可验收的用户故事）；SPK 为特殊 Story（产出是知识/决策而非功能）；
2. 分级明细：按 Feature 成熟度分层——核心闭环层（全量 Gherkin）/ 已规划层（故事句 + 验收要点）/ 远期占位层（一句话故事句）；分层决定"写多细"，非排序依据，排序交 Sprint；
3. 状态：Story 标题带状态位（待开发/进行中/已交付/已废弃），随交付更新，实现现状一目了然；
4. AC 与测试对接：Gherkin AC 落 `.feature` 文件，Story ID 作标签（如 `@S1.1.1`），需求→测试双向追溯；实现层工具选型随代码库演进。

### 分层映射（原优先级 → 成熟度层）

| 层 | 判据 | 覆盖（原优先级） |
|---|---|---|
| 核心闭环层 | 三轮文档评审、需求稳定 | 原 P0 全部（S1.1.1/S1.1.2/S1.1.4、S3.1.1/S3.1.2、S3.2.1/S3.3.1、S4.1.1/S4.1.2/S4.2.1/S4.2.2）+ F0 全部 Spike |
| 已规划层 | 方向明确、细节待校准 | 原 P1（F1.2、F1.3、S4.3.1、EPIC-2 全部）+ S1.3.2 |
| 远期占位层 | 方向性意向 | 原 P2（S3.2.2、S5.1.1）+ F1.4 |

（S1.1.3 迁入 F4.4 仍属核心闭环层；S1.3.2 归已规划层。）

## 3. Story 标题与状态规范

- 格式：`#### S1.1.1（待开发）多条件组合筛选`、`#### SPK-1（已交付）信源可抓取性验证`；
- 状态取值：待开发 / 进行中 / 已交付 / 已废弃；
- 初始全量"待开发"（法务确认行动项按实际标状态）；
- Epic/Feature 标题不带状态；
- 编号纪律：改卡不改号，作废标"已废弃"不删不复用。
