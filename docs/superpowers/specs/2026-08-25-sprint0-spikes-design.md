# Sprint 0 Spike 设计（EPIC-0 去风险）

- 日期：2026-08-25
- 状态：已与用户逐节确认
- 配套：《Product Requirements.md》V0.9、《Architecture.md》V0.8、《Backlog.md》V0.8
- 上游文档：本文档不改变三件套任何结论；Spike 结论将回写三件套

## 0. 背景与定位

文档三件套（需求 V0.9 / 架构 V0.8 / Backlog V0.8）已就绪，仓库尚无代码。按 Backlog 规划，下一步是 EPIC-0 开发去风险（Spike）：以最小成本验证主要技术与领域风险，产出回写需求文档与 ADR，**不交付用户功能**。

**Sprint 0 范围**（已确认）：

- SPK-1 信源可抓取性验证
- SPK-2 LLM 抽取准确率摸底
- SPK-3 LangGraph 端到端验证
- 三个 Spike **严格串行**（SPK-1 供样本 → SPK-2 磨提示词 → SPK-3 端到端）
- SPK-4（第二领域纸面套模）**不做**，留待后续
- 法务确认行动项（招投标/招聘数据边界）由用户在现实中并行推进，结论回写需求 §6

**关键决策**（已确认）：

| 决策点 | 结论 |
|---|---|
| LLM 端点 | 暂用商业 API；架构"端点可配置、支持自有模型服务"约束不变，Spike 不受影响 |
| 试抓深度 | 全量纸面调研 + ≤5 个信源实抓（遵守 robots） |
| 产出物管理 | 试验脚本 + 报告都进 repo（`spikes/` 目录） |
| 时间管理 | 纯产出导向，不设时间盒 |
| SPK-2 样本来源 | SPK-1 实抓存档的真实样本 |
| Spike 依赖 | SPK-1 → SPK-2 → SPK-3 严格串行 |
| 回写机制 | 每个 Spike 完成即回写三件套 + Backlog 状态位，不等 Sprint 0 全部结束 |
| repo 组织 | `spikes/` 独立目录与未来工程代码（`src/`）物理隔离；Spike 代码是一次性学习品，不演进为工程代码 |

## 1. 总体结构

```
pih/
├── docs/                       # 现有三件套 + ADR（回写目标）
├── spikes/
│   ├── README.md               # Spike 总览：目的、纪律、索引
│   ├── spk1-source-probe/      # 信源可抓取性验证
│   ├── spk2-extraction-probe/  # LLM 抽取准确率摸底
│   └── spk3-langgraph-e2e/     # LangGraph 端到端验证
```

**串行依赖链**：

1. **SPK-1**（纸面调研 8 类信源 + ≤5 实抓）→ 信源摸底报告 + 锁定的 ≤10 信源清单 + 存档真实样本内容
2. **SPK-2**（用 SPK-1 样本 20–30 条）→ 抽取准确率评估报告 + 初版抽取提示词 + 端点实测数据
3. **SPK-3**（用 SPK-2 提示词 + 商业 API 端点）→ LangGraph 端到端跑通记录 + 延迟/稳定性数据

**Spike 纪律**（写入 `spikes/README.md`）：

1. 报告与脚本同目录；报告记录：做了什么、看到什么、结论、回写点；
2. Spike 代码是一次性学习品，**不演进为工程代码**——工程实现按架构文档另行落地（`fetch(source) → RawItem[]` 等接口定义已在架构 §4，不怕丢）；
3. 遵守 robots 协议（需求 §6 合规红线）；试抓只取少量样本，不做批量抓取；
4. 每个 Spike 完成即回写三件套与 Backlog 状态位。

## 2. SPK-1 信源可抓取性验证

**目标**：摸底附件 A 的 8 类初始信源的反爬强度与采集可行性，锁定 ≤10 信源清单。检验对象：需求 §7"信源反爬/失效"风险。

### 2.1 纸面调研阶段（全量 8 类）

对每类信源建立**信源摸底卡**（存 `spikes/spk1-source-probe/sources/`，一源一卡）：

| 字段 | 说明 |
|---|---|
| 信源名称 / URL | 如"铁甲网 https://..." |
| 类型 | RSS / 列表页 HTML / API / 变更监控候选 |
| 采集方式预判 | RSS 阅读器 / HTTP+解析 / changedetection.io / RSSHub |
| robots 允许度 | robots.txt 摘录 + 对目标路径的判定 |
| 反爬观察 | 登录墙 / 频控 / 验证码 / 字体混淆 / JS 渲染依赖 |
| 更新频率预估 | 日更 / 周更 / 不定期 |
| 历史内容可达性 | 是否有存档/翻页，能否回溯 ≥3 个月 |
| 纸面结论 | 直抓 / 需适配 / 需变更监控 / 放弃 |
| 实抓候选 | 是/否 + 理由 |

8 类初始信源（附件 A）：CCMA 协会月报、主机厂官网新闻页（2–3 家）、铁甲网、第一工程机械网、中国路面机械网、KHL、国家知识产权局专利公布、千里马招标网。

### 2.2 实抓阶段（≤5 个信源）

从纸面结论选 **≤5 个代表性信源**（覆盖不同采集方式：至少 1 个 RSS、1 个列表页 HTML 解析、1 个变更监控候选），每源抓 **1–3 页列表页 + 3–5 条详情**，产出：

- 每源一份实抓记录：HTTP 状态、页面结构摘要、正文可提取性、遇到的反爬行为、抓取耗时；
- 抓取脚本：遵守 robots + 少量样本纪律，`requests` + 解析即可，不上重型框架；
- 样本正文存档（`.html`/`.md` 原文，存 `spikes/spk1-source-probe/samples/`）——**SPK-2 的样本来源**。

### 2.3 产出与验收

| 产出 | 验收标准 |
|---|---|
| `spk1-report.md` | 8 类信源全覆盖、每源有纸面结论、实抓记录完整 |
| 锁定 ≤10 信源清单 | 每源标注 采集方式 + 层级（L1–L4）+ 频率建议——回写需求附件 A |
| 样本库 ≥15 条正文 | 供 SPK-2 试抽（实抓 5 源 × 3 条左右） |
| 回写 | 需求 §7"信源反爬/失效"风险行更新；附件 A 初始信源改写为锁定版；Backlog SPK-1 → 已交付 |

**边界**：不做登录态抓取、不绕过任何反爬措施、不测需付费/登录的深层内容（纸面判断即可；法务行动项并行覆盖数据边界）。

## 3. SPK-2 LLM 抽取准确率摸底

**目标**：用 SPK-1 真实样本试抽，评估把非结构化正文抽成需求 §4.4 情报 schema 的准确率与提示词工作量。检验对象：需求 §7"LLM 抽取错误"风险。

### 3.1 样本与金答案

- **样本**：SPK-1 样本库选 **20–30 条**，覆盖锁定清单中不同层级（L1–L4）与内容形态（新闻稿/公告/专利/招标）；
- **抽取目标 schema**（对齐需求 §4.4）：主体（公司+产品线）、事件类型（8 类枚举）、事实描述（含量化参数）、推断与判断（含依据）、标签（领域包标签树）、量化参数键值对；
- **金答案**：每条样本人工标注一份标准答案（自标自评，作为对照基准）——准确率评估的前提，工作量最大项。

### 3.2 试抽执行

- 提示词初版按需求 §4.4 字段 + 枚举编写，**结构化输出**（JSON schema 约束，对齐架构 §8"校验失败自动重问"机制预告）；
- 用商业 API **大模型档位**（对齐架构 §9.2：核实与结构化抽取用大模型）；
- 每条样本跑 1 次正式抽取；schema 校验失败自动重问 ≤3 次，同时记录重问率；
- 记录：字段级正确/错误/漏抽、重问次数、每条 token 消耗与耗时。

### 3.3 评估口径

| 指标 | 定义 | 参考阈值（触发架构回写） |
|---|---|---|
| 字段准确率 | 关键字段（主体/事件类型/事实描述/标签）正确条数占比 | < 80% → 提示词工作量超预期，风险升级 |
| 枚举命中率 | 事件类型 8 类枚举选对的比例 | 混淆矩阵记录混淆对 |
| 事实/推断分离合格率 | 推断字段携带依据的条数占比 | < 90% 需加强提示词约束 |
| 重问率 | 需 ≥2 次重问的条目占比 | > 20% 需检讨 schema 复杂度 |
| token 成本 | 每条平均 token + 折算单价 | 回写架构 §9.2 成本公式实测值 |

评估以**逐字段混淆 + 典型错误案例分析**呈现，不只给总分——目的是知道"错在哪"，指导提示词迭代方向。

### 3.4 产出与验收

| 产出 | 验收标准 |
|---|---|
| `spk2-report.md` | 20–30 条全跑、含 5 项指标 + 错误案例分析 |
| 金答案集 | 样本 + 人工金答案 + 抽取结果三方对齐存档（供 SPK-3 复用） |
| 初版抽取提示词 | 磨到字段准确率 ≥80%，或记录"已达当前提示词工程上限" |
| 回写 | 需求 §7"LLM 抽取错误"风险行更新；结论影响架构时（如重问率过高）ADR-004/架构 §8 相应补充；Backlog SPK-2 → 已交付 |

## 4. SPK-3 LangGraph 端到端验证

**目标**：用 SPK-2 磨好的提示词，在 LangGraph 上端到端跑通一次抽取，验证 ADR-004 技术路线。决策语境：ADR-004 后果节。

### 4.1 验证链路

架构 §5.1 主流程的 Spike 简化版：

```
样本文件（SPK-1 存档）→ LangGraph 节点：粗筛(小模型) → 结构化抽取(大模型+SPK-2提示词)
                                                          → schema 校验(失败重问≤3) → 结构化结果落 JSON 文件
```

- 粗筛节点用商业 API **小模型档位**（对齐架构 §9.2 分级），验证"关键词 + 小模型二分类"可行性——粗筛不在 SPK-2 范围，此处一并验证；
- 每个节点是独立函数、显式状态传递——验证 LangGraph 编排模式与架构 §4 模块切分是否吻合；
- 记录：端到端成功率、各节点延迟、重问行为、开发摩擦点（LangGraph 帮了忙/添了乱的地方）。

### 4.2 产出与验收

| 产出 | 验收标准 |
|---|---|
| `spk3-report.md` | ≥20 条样本端到端跑通，节点延迟与成功率数据完整 |
| LangGraph 试验脚本 | 粗筛→抽取→校验 三节点图，可复跑 |
| 回写 | ADR-004 后果节补充实测结论；架构 §5.1 与实际不符时修订流程图；Backlog SPK-3 → 已交付 |

**决策出口**（报告结尾必答）：ADR-004 维持 / 需修订 / 需换方案。若 LangGraph 被证明过重，本 Spike 即换方案证据。

## 5. 法务确认行动项（并行，非 Spike）

招投标（千里马）/ 招聘数据边界 → 结论回写需求 §6 法务表。由用户在现实中推进，Backlog 该行跟随 Sprint 0 完成状态更新。

## 6. 回写机制汇总

每个 Spike 完成时**立即**执行：

| Spike | 回写目标 |
|---|---|
| SPK-1 | 需求 §7 风险行、附件 A 锁定版信源清单、Backlog SPK-1 状态 |
| SPK-2 | 需求 §7 风险行、架构 §9.2 成本实测值、（视结论）ADR-004/架构 §8、Backlog SPK-2 状态 |
| SPK-3 | ADR-004 后果节、（视结论）架构 §5.1、Backlog SPK-3 状态 |
| 法务 | 需求 §6 法务表、Backlog 行动项标注 |

## 7. Sprint 0 完成定义

三个 Spike 报告齐 + 全部回写落盘 + Backlog 四个条目（3 Spike + 法务）状态更新。

完成后进入下一阶段：**工程脚手架 Sprint**——Docker Compose 骨架 + 领域包加载器/校验器（架构 §6.3 钦定的最优先技术任务），届时另起设计。

## 8. 本设计不做的事

- 不写工程代码（脚手架属下一 Sprint，另行设计）；
- 不做 SPK-4 第二领域纸面套模（留待后续 Sprint）；
- 不做批量抓取、登录态抓取、反爬绕过；
- 不改变三件套与 ADR 的任何现有结论——只以实测证据回写。
