````markdown
## EPIC-1 消费者检索与使用情报

**用户目标**：作为消费者（人或 Agent），我在做产品规划/设计/专题分析时，能快速查到可信的竞品情报，并清楚每条情报的可信度与出处。

### F1.1 结构化筛选与浏览

#### S1.1.1（待开发）多条件组合筛选

> 作为消费者，我想按 主体/事件类型/时间范围/标签/置信度/事件核实状态 组合筛选情报列表，以便快速定位某类信息。

```gherkin
AC1: Given 情报库已有 ≥60 条情报
     When 消费者选定"主体=三一 + 事件类型=新品发布 + 近90天"
     Then 列表仅展示同时满足三个条件的情报
     And 每条显示 标题、主体、事件类型、置信度、所属事件核实状态、采集时间

AC2: Given 筛选结果为空
     Then 页面提示无结果，并建议放宽条件

AC3: Given 情报已超过有效期
     Then 列表中该条显示"已过期"标识且排序靠后
```

#### S1.1.2（待开发）情报详情页

> 作为消费者，我想查看单条情报的完整信息（事实描述、推断、来源快照、所属事件状态与核实流转），以便独立判断其可信度。

```gherkin
AC1: Given 任意一条情报
     When 打开详情页
     Then 展示 schema 全部字段（含事实/推断分区展示）
     And 展示所属事件的核实状态与完整状态跃迁历史（自动跃迁标注 system）
     And 提供原文快照与原始链接两个入口
```

#### S1.1.4（待开发）只读查询 API（Agent 消费者）

> 作为 Agent 消费者（如产品规划 Agent），我想以 JSON API 按与 Web 相同的条件组合查询情报，以便程序化消费情报库，而非解析网页。

```gherkin
AC1: 同源一致性（ADR-006）
  Given 情报库已有任意数据
  When 以相同筛选条件分别请求 Web 列表与 JSON API
  Then 返回的情报集合与排序完全一致

AC2: Given 外部系统携带有效凭据调用 API
  When 提交 主体/事件类型/时间/标签/置信度 组合查询
  Then 响应含 情报ID、事实/推断分区、来源引用（URL+快照）、置信度、所属事件核实状态

AC3: Given 缺失或无效凭据的调用
  Then 拒绝访问，不返回任何情报数据
```

### F1.2 自然语言问答

#### S1.2.1（待开发）带引用的情报问答

> 作为消费者，我想用自然语言提问（如"竞品 X 的遥控功能迭代历史"），得到答案且每个结论都标注来源情报、原始链接和置信度，以便判断是否敢采用。

验收要点：
1. 每个事实性结论附引用（情报 ID + 来源名称 + 置信度标签），可点开详情与原文快照；
2. 无置信度高于 C3 的相关情报时，如实回答"暂无可靠情报支持"，不编造；
3. 精确型号 token（如 SY375）可召回（混合检索生效）。

#### S1.2.2（待开发）追问与多轮对话

> 作为消费者，我想对上一轮答案追问（"那 Y 竞品呢？"），系统能理解上下文，以便连续深挖一个主题。

验收要点：
1. 追问省略主体时，沿用上一轮的主体与语境作答。

### F1.3 竞品对比

#### S1.3.1（待开发）功能矩阵对比视图

> 作为消费者，我想勾选 2–5 个竞品，输出功能项对比表（有/无/规划中），以便做竞争分析。

验收要点：
1. 勾选 2–5 竞品 × 功能域（如"远程遥控"）输出对比表，单元格取值 有/无/规划中/未知；
2. 每个"有"的单元格可点击查看支撑情报引用。

#### S1.3.2（待开发）功能矩阵维护

> 作为运营者，我想基于已核实情报维护竞品 × 功能矩阵（有/无/规划中），以便对比视图与专题分析有据可读。

验收要点：
1. 矩阵单元格的取值须关联支撑情报（引用 + 置信度）；
2. 新情报入库或所属事件终态变化时，提示受影响单元格复核。

### F1.4 专题调研（远期占位）

> 作为消费者，我能发起专题调研任务（如"3D 引导系统竞品对比"），智能体限时深挖并产出报告。

## EPIC-2 读者接收情报简报

**用户目标**：作为读者/消费者，我不主动检索时，也能定期收到精选情报，重要事件当日知晓。

### F2.1 定期简报

#### S2.1.1（待开发）周报自动生成与推送

> 作为读者，我想每周一收到上周情报周报（按事件类型分组 + 待核实清单 + 成本与质量指标），以便 5 分钟掌握行业动态。

验收要点：
1. 每周定时（可配置）推送，按事件类型分组、重大事件置顶、每条含置信度标签；
2. 附两项运营指标：采集成功率、待核实积压量；
3. 无新情报仍推送并说明"本周无新增"，不静默。

#### S2.1.2（待开发）月报：趋势与格局

> 作为读者，我想每月收到趋势性归纳（竞品动态对比、值得关注的弱信号），以便把握格局变化。

验收要点：
1. 含各竞品本月事件计数对比、事件类型分布变化、环比突出变化（如"某竞品专利公开数环比 +200%"）；
2. 单列"弱信号"章节——仅出现于 L4 信源且未升级的事件，附置信度；
3. 无新情报仍推送并说明"本月无新增"。

### F2.2 重大事件即时推送

#### S2.2.1（待开发）一级信源重大事件当日推送

> 作为消费者，一级信源（官方）出现新品发布/中标/高管变动时，我想当日收到推送，以便及时响应。

验收要点：
1. 满足 来源层级=L1 且 事件类型∈{新品发布,中标落地,组织人事} 的情报完成入库后，30 分钟内推送（事实摘要 + 置信度 + 详情链接）；
2. 同一事件多源重复报道不重复推送，仅在原推送下追加新来源。

## EPIC-3 运营者维护情报质量

**用户目标**：作为运营者，我能高效处理待核实情报、管理信源与领域包，控制系统质量。

### F3.1 人工核实

#### S3.1.1（待开发）待核实队列处理

> 作为运营者，我想在一个队列里逐条查看待人工处理的情报（低置信、冲突、已具备升级条件的事件），一键确认或证伪，以便控制入库质量。

```gherkin
AC1: Given 存在需人工处理的情报/事件
     When 运营者打开核实队列
     Then 按 置信度升序 + 采集时间升序 排列（低置信、最老的优先）
     And 队列包含三类：低置信度情报、相互冲突情报、已具备升级条件的事件

AC2: Given 运营者对"待核实"事件点击"确认"（已有第二独立信源）
     Then 事件状态跃迁为 多源确认（人工终核），写入 verification_log（操作人、时间、原状态、新状态）

AC3: Given 运营者点击"证伪"并填写理由
     Then 所属事件状态跃迁为 已证伪，理由写入日志
     And 该事件下情报在检索结果中默认隐藏

AC4: Given 事件已具备升级条件（双独立信源）但运营者未处理
     Then 事件保持 单源确认 状态，不自动跃迁为多源确认（终态必须人工）
```

#### S3.1.2（待开发）积压自动降级

> 作为运营者，待核实超过 7 天无人处理的情报自动降级归档，以便队列不被旧数据淹没。

```gherkin
AC1: Given 一条情报待核实状态持续 7 天
     When 定时任务执行
     Then 其检索权重降级，并在巡检报表"积压提醒"中列出
```

### F3.2 信源管理

#### S3.2.1（待开发）信源配置注册与健康监控

> 作为运营者，我在 repo 的 YAML 中注册信源（URL、类型、层级、频率），信源变更走 Git 提交；抓取连续失败时收到告警，以便保持采集不断流。

```gherkin
AC1: Given 运营者在 YAML 中新增信源并提交
     When 流水线加载配置
     Then 系统执行一次试抓取并报告成败，成功才允许启用

AC2: Given 某信源连续 3 次抓取失败
     Then 运营者收到告警（推送至个人渠道），信源标记为"异常"
     And 其他信源采集不受影响

AC3: Given YAML 中信源缺必填字段（如层级）
     Then 配置加载被拒绝并指出缺失字段与行号
```

#### S3.2.2（待开发）信源画像页（远期占位）

> 作为运营者，我想看到每个信源的历史表现（被证伪率、首发率、覆盖领域），以便证据驱动地重估来源可靠性评级。

### F3.3 领域包管理

#### S3.3.1（待开发）领域包 YAML 校验与加载

> 作为运营者，我以 repo 内 YAML 维护领域包（信源、关键词、竞品清单、标签树、模板），加载时自动校验，以便系统切换到其他产品线时零代码改动。

```gherkin
AC1: Given 一份合法的领域包 YAML
     When 流水线加载
     Then 采集关键词、抽取标签树、报告模板立即按新包生效
     And 核心系统无任何代码变更

AC2: Given YAML 缺少必填字段（如标签树）
     Then 加载被拒绝并指出缺失字段

AC3: Given 领域包 YAML 变更已提交
     Then 变更历史可通过 Git 追溯（配置版本化）
```

## EPIC-4 系统自动生产情报（无人值守底座）

**用户目标**：作为消费者，系统 7×24 自动盯信源并产出结构化情报，我看到的永远是新数据，无需任何人手工搬运。

> 技术型 Story：故事以用户价值表述，验收偏技术指标，测试以集成/端到端为主。

### F4.1 自动采集

#### S4.1.1（待开发）按频率自动抓取与快照存档

> 作为消费者，注册的信源按其频率自动更新，且每条原文都存档快照，以便我日后能回溯原文。

```gherkin
AC1: Given 信源配置频率为每日
     When 调度时间到达
     Then 系统自动抓取新内容，并为每条新内容生成原文快照
     And 无快照的内容不允许进入后续流水线

AC2: Given 抓取到与历史内容 URL 指纹相同或相似度 > 阈值 的内容
     Then 自动去重，不产生重复情报

AC3: Given 抓取失败（网络/反爬）
     Then 按指数退避重试 3 次，仍失败计入信源健康统计
     And 原始内容先落盘 inbox，处理失败不丢失、可重放
```

#### S4.1.2（待开发）相关性粗筛

> 作为消费者，系统只把与领域相关的内容送入后续处理，以便情报库不被噪音稀释。

```gherkin
AC1: Given 一条新抓取内容
     When 关键词 + 小模型二分类判定为不相关
     Then 该内容被丢弃并记录到粗筛日志（供漏报审计）
```

### F4.2 自动核实与结构化

#### S4.2.1（待开发）自动结构化抽取

> 作为消费者，每条入库情报都按 schema 填好主体、事件类型、量化参数、标签，以便我能结构化筛选而非读原文。

```gherkin
AC1: Given 一条通过粗筛的内容
     When 结构化抽取完成
     Then 情报记录的 主体/事件类型/事实描述/标签 均非空
     And 事实与推断分字段存放，推断字段必须含依据

AC2: Given LLM 返回的结构化输出未通过 schema 校验
     Then 自动重问（≤3 次），仍失败则条目降级为"待人工"，不丢弃
```

#### S4.2.2（待开发）自动预评级与交叉印证

> 作为消费者，每条情报自动带来源层级与 Admiralty 预评级，同一事件的多源报道自动归并，以便我一眼看出可信度。

```gherkin
AC1: Given 一条新情报
     When 核实引擎处理完成
     Then 其来源层级自动继承自信源配置
     And Admiralty 预评级非空（如 B2）
````
