# ADR-004：流水线编排代码化——LangGraph，不引入低代码平台

- 状态：已接受
- 日期：2026-08-25

## 问题

采集调度与 LLM 处理流水线（粗筛/抽取/评级/聚类/后续 RAG）的宿主形态：低代码平台还是代码？立项早期曾拟用 Dify 编排 + n8n 采集，资源假设确立为 1 人开发运维后需重估。

## 可选方案

### 方案 A：n8n + Dify 低代码栈

- 优点：可视化画布，起步快，无需写编排代码
- 缺点：合计 6 个自部署组件，1 人运维不可持续；工作流无法进 pytest/CI 门禁，与 Backlog 的 Gherkin→CI 约定直接冲突；平台绑定，迁移成本随用量增长

### 方案 B：n8n 采集 + 代码处理混合

- 优点：采集侧省代码
- 缺点：两套心智模型，职责边界模糊，排障跨两个世界

### 方案 C：全代码——LangGraph 编排 + APScheduler 进程内调度

- 优点：可测试、可版本化、可 review；自部署容器 6→4；模型端点可配置不受平台限制
- 缺点：编排代码需自写（AI 辅助开发显著拉低此成本）

## 决策

采用方案 C。处理层全部 LLM 任务以 LangGraph 图实现——LLM 任务一个不少，宿主从可视化画布换为代码；采集调度用 APScheduler 进程内调度。

## 理由

1. 1 人运维约束：组件数与可排障性压倒起步速度；
2. CI 门禁要求流水线可测试——低代码工作流进不了 pytest；
3. AI 辅助开发使"平台省开发"的优势大幅缩水；
4. 语义能力不受影响：LLM 节点在代码中同为第一公民，端点可配置（支持自有模型服务）。

## 后果

- 全部流水线可测试、可版本化、可 review；Dify 绑定风险消失；
- 图结构保持扁平（一条主链，无复杂分支），控制学习与调试成本；
- 前期已验证 LangGraph + 自有模型服务连通性。

### 端到端实测

LangGraph 1.2.11 + MiniMax 端点端到端跑通 25 条金答案样本，验证三节点图（粗筛→抽取→校验）：

- **端到端成功率 92%**（23/25 条产出完整 6 字段 schema）；API 调用成功率 100%（无 429/5xx）。
- **延迟**（min/median/max，ms）：prefilter 4484/7787/30941、extract 3910/10376/28305、validate 0/0/48752、端到端 11931/19738/68429。中位 ~20s/条。
- **粗筛表现**：kept 23/25，2 条假阴性（S09 锂矿公司、S10 碳酸锂期货，金答案均为财报）——粗筛 prompt 口径偏窄，未覆盖上游原材料/期货与工程机械的间接关联。生产期改进：扩 prompt 口径 + 不确定时默认 keep 走人工兜底。
- **重问行为**：5/23 条触发 validate 重问（22%），均最终拿到完整 schema；1 条（S08）重试达 3 次上限。
- **开发摩擦点**：(1) 1.x API 用 `add_edge(START,...)+add_conditional_edges` 替代 0.x 的 `set_conditional_entry_point`（deprecated alias）；(2) 粗筛小模型 MiniMax-M2.7 仍为推理模型，耗时与大模型同量级，"小模型省时间"预期在推理档位下不成立，生产期粗筛宜换非推理小模型。
- **决策结论**：ADR-004 维持。编排路线成立，摩擦点均在 prompt/模型选型层面，不触及编排架构。
