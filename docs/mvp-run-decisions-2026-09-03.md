### D8 【架构】TASK-4.01.01 调度器设计：APScheduler BlockingScheduler 进程内 `pih work`，每启用源一 job，退避重试 ×3 ✅
- **决策**：`pih work` 长驻进程：APScheduler 按信源 `fetch_frequency`（hourly/daily/weekly）建 interval job（含小抖动错峰）；job 内 collect_source；抓取异常按指数退避（2s/4s/8s）重试 3 次；成功清零连续失败计数，失败 +1；每次调度写 pipeline_run（吞吐/失败/时长）；结构化日志 pih.work。
- **理由**：ADR-004/008 既定（APScheduler、worker 进程内）；无新自部署组件（DoD#2）；compose 加 pih-worker 服务（单镜像双角色目标态落地）。退避在进程内同步做（单机单人，无需持久化退避状态）。
- **被否**：celery/RQ（违 ADR-007 不引入 MQ）；cron 系统级（不可测试、留痕弱）；退避状态入库（过度设计）。

### D9 【数据】健康统计载体：`source` 表加列（consecutive_failures / last_failure_at / last_failure_reason / last_success_at），不加表 ✅

- **理由**：健康是「每源一行」的标量状态，独立表反而需 1:1 JOIN；source_sync upsert 已有 upsert 路径可挂回写。信源页原型本就有「健康」列（当前恒「正常」未上线）。
- **被否**：从 dead 行实时聚合（dead 是条目级死信，抓取失败才落 dead 行、且有 url 幂等去重，不能表达「连续 N 次」语义）。

### D10 【行为】TASK-4.02.01 告警触发与去重：连续失败计数达到 3 → 生成一条站内信；同源持续失败不重复告警，成功恢复后再失败重新计数 ✅
- **决策**：notification 表（id/type/source_id/title/body/read_at/created_at）；触发点=连续失败计数自增后 ==3（恰好达到，非每次失败都发）；恢复成功时不发恢复通知（留演进）。

- **被否**：每次失败都发（风暴）；告警后静默 24h（时间窗需时钟依赖，单机无必要）。
