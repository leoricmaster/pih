### D2 【口径】TASK-1.02.01 AC5 聚类口径收窄：主体归一×事件类型×±7天时间窗，**不含内容相似度阈值** ✅
- **决策**：聚类规则按 doc-2 §4 权威口径（主体归一〔领域包别名〕× 事件类型精确 × ±7 天窗），AC5 中「内容相似度超阈值」不实现。
- **理由**：doc-2 §4 与 README 均为此口径；「内容相似度」属模糊/近重复语义（TASK-9.1 演进单），且事件聚合粒度=主体×类型已能表达「同一事件」。与 1.01.02 的 AC2 收窄先例同构，将以 task comment 记档。
- **被否**：引入 embedding 相似度（需 pgvector 检索列 + 阈值标定，超出 MVP 且无评估手段）。

### D3 【口径】TASK-1.02.01 AC1「推断字段必须含依据」→ validate 节点强制（缺依据判校验失败走重问/降级） ✅
- **决策**：`validate_pred` 增加「推断与判断」非空时须含依据标记（`依据：` 或括号内依据串）的校验；不合格→重问→仍不合格→needs_manual。
- **理由**：AC 字面「必须含依据」是硬约束，prompt 引导（现状）不保证；校验在既有重问机制内闭环，零新组件。
- **被否**：仅 prompt 引导不校验（不满足 AC 字面）；独立小模型判依据（新增调用成本，无必要）。

### D4 【口径】TASK-2.01.01 置信度筛选语义：**≥ 选中档**，按来源可靠性 A–F 映射（A 最优），单轴筛选 ✅
- **决策**：筛选器为「置信度 ≥ X」下拉（选项 A/B/C/D/E/F，来自领域包 ranking.reliability 键集），匹配 `admiralty_code` 首字符（来源可靠性轴）≤ 所选档（A<B<C…）。
- **理由**：原型即「≥ B ▾」；信源页图例已教育用户「可靠性看 A–F」；Admiralty 短板语义（两维取小）已由排序承载，筛选保持单轴简单可预期。
- **被否**：按 map(admiralty) 数值区间筛（用户难口头沟通，违背 §6.3 词表初衷）；双轴分别筛（原型无此 IA）。

### D5 【IA】TASK-2.02.02 核实页落位：侧栏「运营」组新增「核实」页；三类队列纵向分区 + 积压提醒区置顶 ✅
- **决策**：`GET /verify` 核实页（nav「核实」入运营组）；页面结构（自上而下）：①积压提醒区（超 7 天待核实事件，按滞留时长排序）②已具备升级条件的事件（确认/证伪按钮+理由表单）③低置信度情报④待人工条目（needs_manual，链接详情）。排序遵守 AC1：置信度升序+采集时间升序。
- **理由**：原型注明「F 核实队列随核实层（未来）呈现」——本故事即该未来，IA 需新设计；挂运营组因消费者不核实（doc-2 §2 角色分工）；积压置顶因它是运营健康信号。**原型将反向更新**（新增核实页节，R2 先例闭环）。
- **被否**：并入情报页第三 tab（页内已有 检索/收件箱 两 tab，再塞运营职责破坏「消费区/运营」导航分层）。

### D6 【口径】TASK-2.02.02「低置信度情报」阈值：Admiralty 可信度 ≥4（存疑档起）或可靠性 ≥D，取并集，常量进代码、领域包可调留演进 ✅
- **决策**：低置信度 = admiralty_code 任一维度进入低档（可信度 4–6 或可靠性 D–F）且未挂已证伪事件；阈值常量先落代码（`consume/query_service.py` 或 labels 附近），领域包 ranking 节扩展留演进。
- **理由**：NATO 分档 4=存疑，语义自洽；避免为 MVP 引入新配置面。**明日可改**（若你觉得队列太长/太短，调阈值即可）。
- **被否**：固定 credibility≥4 单轴（漏掉 E5 这类双低条目）；立即做领域包可配置（YAGNI，无第二领域消费方）。

### D7 【行为】TASK-2.02.02 AC3 已证伪默认隐藏：QueryService 默认排除所属事件=refuted 的条目（显式 `event_status=refuted` 可查） ✅
- **决策**：检索默认 WHERE 排除 refuted 事件条目；显式指定 event_status=refuted 时可见（审计可达）。
- **理由**：doc-2 §6.3「已证伪 0（默认不出现在结果）」的字面落实；现状排序权重 0 只会排末尾不会隐藏，不满足 AC3「默认隐藏」。与 1.01.02「filtered_out 不进检索、显式可筛」同构。
- **被否**：仅靠 score=0 排序沉底（不等于隐藏）；物理删除（违背留痕纪律）。

### D8 【架构】TASK-4.01.01 调度器设计：APScheduler BlockingScheduler 进程内 `pih work`，每启用源一 job，退避重试 ×3 ✅
- **决策**：`pih work` 长驻进程：APScheduler 按信源 `fetch_frequency`（hourly/daily/weekly）建 interval job（含小抖动错峰）；job 内 collect_source；抓取异常按指数退避（2s/4s/8s）重试 3 次；成功清零连续失败计数，失败 +1；每次调度写 pipeline_run（吞吐/失败/时长）；结构化日志 pih.work。
- **理由**：ADR-004/008 既定（APScheduler、worker 进程内）；无新自部署组件（DoD#2）；compose 加 pih-worker 服务（单镜像双角色目标态落地）。退避在进程内同步做（单机单人，无需持久化退避状态）。
- **被否**：celery/RQ（违 ADR-007 不引入 MQ）；cron 系统级（不可测试、留痕弱）；退避状态入库（过度设计）。

### D9 【数据】健康统计载体：`source` 表加列（consecutive_failures / last_failure_at / last_failure_reason / last_success_at），不加表 ✅
- **决策**：迁移 0003 给 source 表加 4 列（含 downgrade）；collect 成功/失败路径回写；信源页健康列读 DB（与 pack YAML 六字段并示）。
- **理由**：健康是「每源一行」的标量状态，独立表反而需 1:1 JOIN；source_sync upsert 已有 upsert 路径可挂回写。信源页原型本就有「健康」列（当前恒「正常」未上线）。
- **被否**：从 dead 行实时聚合（dead 是条目级死信，抓取失败才落 dead 行、且有 url 幂等去重，不能表达「连续 N 次」语义）。

### D10 【行为】TASK-4.02.01 告警触发与去重：连续失败计数达到 3 → 生成一条站内信；同源持续失败不重复告警，成功恢复后再失败重新计数 ✅
- **决策**：notification 表（id/type/source_id/title/body/read_at/created_at）；触发点=连续失败计数自增后 ==3（恰好达到，非每次失败都发）；恢复成功时不发恢复通知（留演进）。
- **理由**：AC1 字面「连续 3 次抓取失败→收到未读站内信」；episode 语义（reset-on-success）避免告警风暴；单用户系统无需更复杂的告警窗口。
- **被否**：每次失败都发（风暴）；告警后静默 24h（时间窗需时钟依赖，单机无必要）。

### D11 【IA】通知呈现：base.html 顶栏铃铛（未读数角标）+ 下拉最近通知 + 「查看全部历史」页 `/notifications` ✅
- **决策**：照原型 topbar 实现：铃铛+未读数；下拉列出最近未读（含信源名与失败原因）；`/notifications` 历史页（未读/历史分组，可标记已读 POST）；侧栏不加入口（原型明确「仅经铃铛可达」）。
- **理由**：原型 IA 已完整定义本节（notifdrop + notif 页），首次照抄即可；TASK-3.01 假设命中提醒将来复用同一通知面。
- **被否**：侧栏「通知」navlink（原型显式移除过）。

### D12 【运行】过夜演示形态：`pih work`（调度器）+ uvicorn web 双进程留机运行，演示数据今晚种子 ✅
- **决策**：收尾时：①真实采集 ≥2 源 → LLM 实弹处理 → 聚类挂事件 → 人工核实一部分（造出各状态样本）②uvicorn 起 :8000 ③pih work 后台跑（每日频率源次日晨自动新采集可见）。
- **理由**：验收从 Web 页面视角（记忆：acceptance-web-perspective）；「到点可见」的活体证据比截图强。进程用 nohup 脱离会话，日志落 `logs/`（gitignore）。
