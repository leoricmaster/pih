## 1. 架构愿景与约束

**一句话**：一条"采集 → 核实 → 结构化 → 存储 → 消费"的情报流水线，核心域模型行业无关，行业知识以领域包（Domain Pack，repo 内 YAML 配置）注入。

**四条贯穿性约束**（所有模块设计不得违反）：

1. **通用性在模型层，不在业务层**：核心代码不出现任何"挖机/工程机械"字样，行业知识全部来自领域包配置；
2. **一切 AI 产出可回溯**：每条入库情报必须能追溯到原文快照与来源，无快照不入库；
3. **人是核实的最终环节**：AI 只做预核实与分级；`多源确认` 与 `已证伪` 两个**终态**的跃迁必须经人工，中间态可自动流转（见 4.2 状态机）；
4. **1 人可运维**：系统须可被 1 人监控、修复、恢复——每个自部署组件都占用升级/备份/排障精力，引入须论证；优先可测试的代码资产，拒绝工作流黑盒。

## 2. 系统上下文

```
信源（RSS/网页/API/文件*）      消费者（人：Web / Agent：API）
   │                                │
   ▼                                ▼
┌─────────────────────────────────────────┐
│              情报中心                     │

└─────────────────────────────────────────┘
   │                │              │
   ▼                ▼              ▼
LLM 服务        对象存储        推送渠道（企微/邮件）
```

## 3. 逻辑架构（模块视图）

```
┌─────────────────────────── 消费层 ───────────────────────────┐
│ 查询服务(只读Web+JSON API*¹) │ 推送服务 │ 报告服务(周/月报*)        │
├─────────────────────────── 存储层 ──────────────────────────┤
│ 情报库(PG) │ 竞品资产库(PG) │ 向量+全文索引(pgvector) │ 快照库(MinIO)│
├─────────────────────────── 处理层 ──────────────────────────┤
│ 核实引擎 │ 结构化抽取器 │ 事件聚类器(交叉印证) │ 时效管理器      │
│           （以上由 LangGraph 编排，LLM 任务节点化）             │
├─────────────────────────── 采集层 ──────────────────────────┤
│ 调度器(APScheduler) │ 信源适配器(插件) │ 去重器 │ 相关性粗筛      │
├────────────────────── 横切（配置与治理） ─────────────────────┤
│ 领域包(YAML+校验) │ 核实操作(CLI/极简页) │ 可观测性          │
└────────────────────────────────────────────────────────────┘
*¹ Web 与 JSON API 同源（ADR-013）；* RAG 问答与周/月报为 M2
```

## 4. 核心数据流

### 4.1 互联网情报主流程（M1）

```
调度器触发 → 适配器抓取 → 原始内容落盘(inbox) → 快照存档
  → 去重 → 粗筛
  → LLM 结构化抽取（领域包注入：主体清单/标签树/提示词）
  → 核实引擎预评级（来源层级 + Admiralty + 事实/推断分离）
  → 事件聚类（命中已有事件？ 附源/进入单源确认 : 新建事件,状态=待核实）
  → 写入情报库
  → (M2) 重大事件即时推送 + 汇入周报
  → 人工核实操作确认/证伪（写 verification_log）
```

### 4.2 状态机（核实状态，唯一事实源）

**层级**：核实状态挂在**事件层**（`event` 表）；情报条目（`intel_item`）不持有独立状态，详情页展示"所属事件的状态 + 本条目的核实日志"。

**状态集**：`待核实 → 单源确认 → 多源确认`；`已证伪`；`已过期`（横切标记，非终态，可叠加于任何状态并触发复核）。

| 跃迁 | 触发者 | 触发条件 | 说明 |
|---|---|---|---|
| （初始）→ 待核实 | 自动 | 新事件创建 | 新聚类事件的默认初始态 |
| （初始）→ 单源确认 | 自动 | 新情报命中已有事件 | 见下"初始态规则" |
| 待核实 → 单源确认 | 自动 | 该事件获得第二个独立信源 | 中间态自动流转 |
| 单源确认 → 多源确认 | **人工** | 双独立信源 + 运营者确认 | 事件标记"已具备升级条件"后进人工队列 |
| 待核实/单源确认 → 已证伪 | **人工** | 运营者证伪（必填理由） | 终态 |
| 任何状态 → 已过期 | 自动 | 超过有效期 | 降权 + 复核提醒，可恢复 |

**初始态规则**：新情报独立成新事件 → 事件初始 `待核实`；新情报聚类命中已有事件 → 条目挂入该事件，若此为第二个独立信源，事件自动 `待核实 → 单源确认`。

**两层状态同步规则**：事件状态即聚合展示状态；条目级 `verification_log` 记录每一次跃迁（自动跃迁也记，操作者标 `system`），详情页时间线 = 事件状态跃迁 + 条目挂入历史。

### 4.3 检索流程（M1 筛选；M2 RAG）

```
M1:  筛选条件（主体/事件类型/时间/标签/置信度）
     → SQL 结构化过滤 → 按 score(置信度,时效) 排序 → 列表/详情
     （出口两类：Web 页面与 JSON API，同源，见 ADR-013）
M2: 自然语言提问 → 意图解析（问答/筛选/对比）
     → 混合召回（BM25 关键词 ∪ 向量） + 结构化过滤
     → 按 score(置信度,时效) 重排 → LLM 生成答案（强制引用情报ID+来源+置信度）
```

**排序函数定义**：

`score = W_c × map(admiralty) × decay(now - 采集时间)`

- `map(admiralty)`：来源可靠性 A–F → {A:1.0, B:0.8, C:0.6, D:0.4, E:0.2, F:0}；信息可信度 1–6 → {1:1.0, 2:0.8, 3:0.6, 4:0.4, 5:0.2, 6:0}；两者取小（短板决定）后线性组合；
- `decay`：分段函数——有效期前 1/3 不衰减，中段线性衰减至 0.5，过期后 0.3 并叠加"已过期"标记；
- `W_c`：事件状态权重——多源确认 1.0 / 单源确认 0.8 / 待核实 0.5 / 已证伪 0（默认不出现在结果中）；
- 初始权重如上，作为领域包可调参数（`ranking:` 节），M1 运行期观察调优。

## 5. 数据架构

- **PostgreSQL** 为单一事实源：`intel_item`、`entity`、`source`、`event`、`verification_log`、`domain_pack`、`competitor_profile`、`feature_matrix`、`param_matrix`；
- **pgvector** 承载情报摘要向量 + **PG 中文全文检索**（zhparser 或 pg_jieba）承担 BM25 侧——混合检索在单库内闭环（M1 规模 < 10 万条，无需独立向量库）；
- **MinIO** 存原文快照与附件，`intel_item.snapshot_id` 关联；
- 事件（`event`）与情报（`intel_item`）一对多：交叉印证的载体，核实状态挂事件层、来源各挂各的；
- `verification_log` 同时是未来信源画像的数据底座（需求文档 §4.1）。

## 5A. 流水线可靠性

**语义**：at-least-once + 幂等处理。核心原则——**原始内容先落盘，处理永远可以重放**。

| 环节 | 失败处理 |
|---|---|
| 抓取 | 适配器重试（指数退避 ×3）→ 失败计入信源健康，连续 3 次告警 |
| 落盘后处理 | inbox 原始内容持久化；任一阶段失败，条目停留该阶段可重试，不回滚已成功阶段 |
| LLM 调用 | 重试 ×3 + 结构化输出校验失败自动重问；持续失败降级为"待人工"，不丢弃 |
| 入库 | 幂等键 = 快照内容指纹；重复处理不产生重复条目 |
| 死信 | 重试耗尽的条目进 `dead_letter` 表，CLI 可查看/重放/丢弃 |
| 状态跃迁 | 全部走状态机模块统一入口，自动跃迁写日志（操作者=`system`），禁止绕过 |

**可观测性**：各阶段吞吐/失败率/积压量为默认指标；采集成功率、粗筛通过率、核实积压量每日 CLI 报表推送（1 人运营的巡检入口）。

## 7. 关键架构决策（ADR）

### ADR-001：核心域模型行业无关，行业知识封装为领域包
- **背景**：系统需从挖机智能化扩展到任意产品线；但当前仅 1 个领域样本。
- **决策**：核心只定义 主体—事件—情报—来源—置信度 五元模型；信源、关键词、竞品清单、标签树、报告模板、抽取提示词打包为 Domain Pack。**M1 形态 = repo 内 YAML 配置文件 + schema 校验，不是插件机制**；插件化推迟到第二个领域包真实接入之后。
- **后果**：切换/新增领域 = 改 YAML；抽象风险被限制在配置层。被过早抽象毒害的可能性大幅下降。
- **被否决备选**：完整插件机制（领域包带代码）——单领域样本下无法证伪通用性设计，rule of three 未满足，否决。
- **验证机制**：Sprint 0 Spike ④——用第二个假想领域（物流机器人）纸面套一遍五元模型与领域包 schema，记录覆盖缺口；通用性验收推迟到第二领域真实接入。
- **Backlog 提示**：领域包 YAML schema 定义与加载器是最优先技术任务。

### ADR-002：核实采用"AI 预核实 + 人工终核"两段式
- **背景**：全自动核实不可靠，全人工不可持续；且"跃迁全人工"与"双源自动升级"两种表述曾并存，需统一。
- **决策**：中间态（待核实→单源确认）自动流转；**两个终态（多源确认/已证伪）必须经人工操作**，全程留痕（verification_log，自动跃迁操作者=`system`）。
- **后果**：人工精力集中于终态判断；核实操作（CLI/极简页）是 P0；积压治理（7 天自动降级）进入需求。
- **被否决备选**：全自动状态跃迁（错误情报污染下游检索，信任崩塌系统即失败）；全人工跃迁（1 人运营下队列必然积压）。

### ADR-003：置信度采用 Admiralty Code（来源 A–F × 信息 1–6）
- **背景**：需要统一、可沟通的可信度语言。
- **决策**：借用威胁情报成熟标准，单字符双维度，如 B2；LLM 预评级与人工评级共用同一词表；评级最终证据驱动（信源画像为后续方向，基于 verification_log 历史结局重估）。
- **后果**：比自定义百分制更易培训与对齐。
- **被否决备选**：百分制/星级置信度——连续值难对齐、难口头沟通、LLM 输出不稳定，否决。

### ADR-004：事件（Event）与情报（IntelItem）分离建模
- **背景**：同一事件多信源报道，需交叉印证。
- **决策**：情报挂在来源上，事件聚合情报，核实状态记在事件层；条目详情页展示"所属事件状态 + 条目核实日志"。
- **后果**：去重/聚类成为独立模块；避免"同一事件多条记录状态打架"。
- **被否决备选**：状态挂条目、事件仅作分组标签——两条目状态可互相矛盾，交叉印证语义无法自洽，否决。

### ADR-005：原文快照强制存档，无快照不入库
- **背景**：网页会改会删，AI 会抽错，必须可回溯。
- **决策**：采集即存档（MinIO），检索引用同时给出快照与原始链接。
- **后果**：存储成本可忽略（文本为主）；合规上对外分享仅给链接与摘要。
- **被否决备选**：只存 URL——链接腐烂后情报不可回溯，整个"可回溯"约束崩塌，否决。

### ADR-006：Agent 编排代码化——LangGraph，不引入低代码平台
- **背景**：曾拟用 Dify 编排、n8n 采集；资源假设确立为 1 人开发运维后重估。
- **决策**：处理层（粗筛/抽取/评级/聚类）与后续 RAG 全部用 **LangGraph 代码**实现；采集调度用 APScheduler 进程内调度。LLM 任务一个不少，宿主从可视化画布换为代码。
- **理由**：① n8n + Dify = 6 个自部署组件，1 人运维不可持续；② 低代码工作流无法进 pytest/CI 门禁，与 Backlog 的 Gherkin→CI 约定直接冲突；③ AI 辅助开发显著拉低写代码成本，"平台省开发"的理由被削弱；④ 语义能力不受影响——LLM 节点在代码中同为第一公民，模型端点可配置（自有模型服务）。
- **后果**：全部流水线可测试、可版本化、可 review；Dify 绑定风险消失；容器 6→4。
- **被否决备选**：n8n + Dify 平台栈（上述四条理由）；n8n 采集 + 代码处理混合（两套心智模型 + 职责边界模糊，否决）。
- **Backlog 提示**：LangGraph 图结构 + 领域包注入机制是最优先技术任务之一。

### ADR-007：M1 前端为极简只读 Web
- **背景**：曾拟用 Dify 界面 + 飞书多维表格，但无法交付 Backlog 详情页 AC（引用跳转、核实历史、快照入口）。
- **决策**：FastAPI + 服务端模板，交付筛选列表 + 情报详情两类页面（含事件状态、核实时间线、快照入口）；人工核实先用 CLI/极简表单，Web 化为后续方向。
- **后果**：约 3–5 人日；S1.2.x 全部 AC 可交付；检索体验（北极星指标载体）有保障。
- **被否决备选**：Dify 聊天 + 多维表格（交付不了详情页 AC）；完整自研 Web（过度，M1 单用户不需要）。

### ADR-008：LLM 分级调用控成本，端点可配置
- **决策**：粗筛/去重用小模型，核实与结构化抽取用大模型，报告生成用大模型；全部端点可配置（支持自有模型服务），模型路由集中管理（放配置中心）。
- **成本公式**：月成本 ≈ Σ_任务(信源数 × 日抓取量 × 粗筛通过率 × 平均 token × 单价)。以 10 信源、日均 80 条、通过率 30%、粗筛小模型 + 抽取大模型估算，月成本约 200–400 元（自有服务折算算力）；上线后以实际用量校准，周报含成本项。
- **后果**：换模型/换端点不改代码；成本可预测可监控。
- **被否决备选**：全旗舰模型（成本数倍且粗筛无需强模型）；全小模型（抽取准确率不达标）。

### ADR-009：单一 PostgreSQL + pgvector + PG 全文检索，不引入独立向量库
- **决策**：M1 数据量下 pgvector + PG 中文全文检索（BM25 侧）足够；检索接口抽象，后续可平滑切 Qdrant/ES。
- **后果**：运维组件数最小化，单机 Compose 可跑；混合检索（见 ADR-011）在单库内闭环。
- **被否决备选**：独立 Qdrant/Milvus（M1 规模下纯增运维负担）；纯向量检索（中文精确 token——竞品型号如 SY375——召回弱，否决）。

### ADR-010：人工情报走同一流水线，仅入口不同
- **背景**：参会见闻、访谈纪要与互联网情报同构。
- **决策**：人工录入网关产出 `RawItem`（来源类型=人工，来源可靠性默认 A/B 级），复用核实/结构化/存储全链路。
- **后果**：M1 的 RawItem 模型与流水线接口必须预留该来源类型，避免后续返工。
- **被否决备选**：人工情报独立管道（两套核实/存储逻辑，后续维护双倍，否决）。

### ADR-011：混合检索——BM25 关键词 ∪ 向量召回
- **背景**：行业查询两类典型形态——语义型（"遥控功能迭代史"）与精确型（"SY375"）；纯向量检索在精确 token 上召回弱。
- **决策**：M2 RAG 采用两路召回（PG 中文全文 + pgvector）+ 结构化过滤 + 统一重排（4.3 排序函数）；两路权重为领域包可调参数。
- **后果**：精确型号查询与语义查询都有保障；实现复杂度可控（单库内）。
- **被否决备选**：纯向量（精确 token 弱）；纯关键词（语义泛化弱）。

### ADR-012：流水线 at-least-once + 幂等
- **背景**：无人值守系统必须回答"LLM 调用失败/半处理状态怎么办"。
- **决策**：原始内容先落盘 inbox 再处理；各阶段幂等（内容指纹为幂等键）；重试耗尽进死信表；状态跃迁统一走状态机入口并全部留痕。详见 5A。
- **后果**：任何失败可重放，不丢数据；重试与死信是默认设计而非补丁。
- **被否决备选**：fire-and-forget（失败即丢，与"无快照不入库"的严谨性矛盾）；恰好一次投递（分布式语义复杂，单机规模不需要）。

### ADR-013：Web 与只读查询 API 同源交付
- **背景**：消费者角色的承担者不限于人——Agent（如产品规划 Agent）需程序化消费情报库；若为 API 单独建一套查询服务，过滤与排序逻辑必然分叉漂移。
- **决策**：查询服务为单一事实源，只读 Web 页面与 JSON API 是同一 FastAPI 应用的两类出口，共用结构化过滤、score 排序（4.3）与引用拼装。M1 API 只读（筛选列表 + 详情，REST）；M2 RAG 的 `ask()` 对人与 Agent 同一接口。鉴权 M1 从简（内网部署 + 静态 token），权限体系为后续方向；写入侧——Agent 贡献者线索回写——复用人工录入网关（ADR-010），M1 仅预留来源类型与接口，不交付。
- **后果**：Agent 消费者接入零额外开发；Web/API 结果一致性天然保障；北极星指标（检索次数）可按 Web/API 分别计数汇总。
- **被否决备选**：仅 Web（Agent 只能解析页面，脆弱且不可持续）；独立 API 服务（1 人运维下多一个组件，两套查询逻辑必然漂移，否决）。
